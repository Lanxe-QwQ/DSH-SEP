# 记忆修复候选 memory-repair.1

这是基于公开 Beta.4／DSH 0.2.1-rc.2 的隔离修复候选，不代表已经安装或公开发布。内部宿主适配版本继续是 `0.2.1-beta.3-rc2-adapter.1`；本轮以 buildId、Git 提交和实际文件哈希区分，不以宿主 RC 标识宣称 SEP 达到 RC。

## 行为变化

1. 普通召回、查询、上下文注入、候选提取和重复工具步骤都不刷新 `lastUsedAt`。文本去重只合并来源。直接用户确认或更正已有的明确 ID/修订号，以及明确重新启用，才走受控使用路径。同一会话中的同一用户消息对同一记录不能借更换工具 eventId 重复续期。
2. BM25 的汉字双字组合仅来自原文连续汉字段，不能跨标点、空白、英文、数字或 emoji。按 Unicode 码点处理，英文数字词段不吞掉随后汉字。单字、合法双字组合和 `Intl.Segmenter` 混合检索继续保留，BM25 的 k1=1.2、b=0.75 与 IDF 公式不变。因此单字重合仍可能召回文本；本修复不承诺所有语义匹配正确。
3. 记录归档、撤回、永久删除或被另一确认值替代时，在同一活跃目录事务中维护剩余候选的冲突关系。关系变化增加修订号并记录审计，但不改正文时间。其他未确认候选不会被一条确认静默批准或删除。

已有悬空冲突按 owner、语义槽和精确 ID 核验撤回/删除标记或一致的冷归档。未知、跨作用域或损坏的依据返回 `MEMORY_CONFLICT_UNVERIFIED`。新竞争者或旧视图不能被旧确认归档：先持久提交一次关系刷新，返回 `status: conflict_refresh_required`、`code: MEMORY_CONFLICT_REFRESH_REQUIRED` 及新修订；重新审阅后再确认。旧修订继续返回 `REVISION_CONFLICT`。不通过抛错回滚刚修好的元数据。

## 时间、容量与数据兼容

- 保持每 owner 活跃 L2/L3 合计 500 条；项目 owner 与显式共享用户 owner 分开计数。先检查撤回排除、再去重，只有新增时检查增长容量。满额时在当前事务内按原政策归档可退出的记录，冷载荷可靠保存后才发布活跃目录。没有可回收项仍返回 `MEMORY_LIMIT`；归档域满或写入失败不会假称腾位成功。
- 选择、手动召回、自动捕获候选与维护使用相同资格规则，并纳入完整授权项目范围内的共享依赖。物理维护节流不让明确到期内容继续注入上下文。
- 原有候选/临时事项 30 天、已关闭任务 7 天等规则保留；置顶、未完成任务及有效依赖继续保护。已确认习惯/个人重要数据没有新增统一 TTL。L4 仍按需检索，普通未命中不自动访问 L4。
- 保留既有 ID、正文、作用域及所有历史时间，不清空数据库、索引、账本或预算。无法重建过去真实使用时间；曾被误续期的记录可能仍需等待当前窗口到期。
- 记录/目录 schema 仍为 1。关系绑定、有限审计及使用回执放在原有 JSON events 域，不增加严格 record 字段。现有事件/归档容量保护不扩大；这不是无限存储承诺。旧代码能读这些字段并不证明降级后的写入语义安全，因此不自动降级或以旧快照覆盖新业务数据。
- RAG 索引及冷归档保存正文片段，本套件检索时分词。本轮不要求重建整库；没有引入混用旧词项的持久分词缓存。

## 当前验证范围

Windows 与 D 盘承载的 WSL2 Ubuntu/ext4 运行真实官方 SDK、受管 JSON 存储和 P2；模型适配器为合成，不调用付费 API。核心定义 65 项，另有真实存储 3 轮、官方 Loader/组合流程及既有消费者回归。重复轮次与新定义分开计数，详见源码 `tools/memory-repair/README.md` 和本轮结果索引。

macOS 原生复验尚未运行，不以 Windows/Linux 成绩替代。既有平台预览、签名、公证、物理输入和完整认证限制继续保留。新日常安装、公开 Release 和 GitHub 上传均需另行授权；当前日常程序保持原位。
